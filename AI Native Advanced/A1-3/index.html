Git은 원고를 고쳐가며 버전을 남기는 편집자의 일입니다.

💻 내 컴퓨터 | ☁️ GitHub

위 버튼을 누르면 그 명령이 어느 칸에서 어느 칸으로 옮기는지 그림에 표시됩니다.

쉬운 말 사전

Git 용어는 처음 보면 다 낯섭니다. 이 서비스는 쉬운 말을 앞에 두고 원래 용어를 나란히 적습니다. 검색할 때는 원래 용어가 필요하니까요.

먼저, Git과 GitHub는 다른 것입니다

이름이 닮아서 같은 것으로 아는 분이 많습니다. 하나는 내 컴퓨터에 까는 프로그램이고, 하나는 인터넷에 있는 웹사이트입니다.

버전을 남겨주는 프로그램

Git

내 컴퓨터에 깔아서 씁니다. 원고를 고칠 때마다 “여기까지”를 남겨두고, 나중에 그때로 돌아갈 수 있게 해줍니다. 인터넷이 없어도 다 됩니다.

💻 맨 위 그림에서 내 컴퓨터 안에 있는 칸은 전부 Git이 하는 일입니다

다 같이 보는 웹사이트

GitHub

내 컴퓨터에 쌓인 기록을 올려두는 곳입니다. 동료도 여기서 내 원고를 봅니다. 올리고 받아오는 것 말고는 하는 일이 없습니다.

☁️ 맨 위 그림의 공유 폴더 한 칸만 GitHub입니다

GitHub에 가입하지 않아도 Git은 그대로 씁니다. 반대는 안 됩니다. 이 한 줄만 기억하면 둘을 헷갈릴 일이 없습니다.

올려두는 곳은 GitHub 말고도 있습니다(GitLab, Bitbucket 등). 어디를 쓰든 Git 쓰는 방법은 똑같습니다.

자주 나오는 말

  • 책상

    작업 폴더 working directory

    지금 파일을 실제로 고치고 있는 자리. 편집기에서 보이는 게 여기입니다. 여기서 고친 것은 아직 어디에도 기록되지 않습니다.

  • 버전 하나

    커밋 commit

    그때까지 고친 원고 전체를 통째로 보관해 둔 것. 한 번 남겨두면 언제든 그때 원고로 돌아가 볼 수 있습니다.

  • 이번 버전에 넣을 것 고르기

    스테이징 staging · index

    파일 10개를 고쳐도 고른 3개만 그 버전에 들어갑니다. 이 고르는 단계가 Git과 그냥 백업의 결정적 차이입니다.

  • 내 기록함

    로컬 저장소 .git

    남긴 버전이 쌓이는 곳. 내 컴퓨터 안에 있습니다. 인터넷이 끊겨도 버전을 남겨둘 수 있는 이유입니다.

  • 작업본

    브랜치 branch

    같은 원고에서 갈라져 나와 따로 고쳐나가는 작업본. “지금 여기까지”를 가리키는 이름표이기도 해서, 새 버전을 남기면 이름표도 따라 옮겨갑니다. 작업본을 하나 더 만들면 원고가 두 작업본으로 나뉘어 각자 고쳐나갈 수 있습니다.

  • 지금 보고 있는 곳

    HEAD

    여러 작업본 중 지금 펼쳐놓고 보고 있는 쪽. 보통은 main 작업본과 같은 자리에 있습니다.

  • 공유 폴더

    원격 저장소 remote · GitHub

    팀이 함께 보는 공유 폴더. 내가 보내기 전까지는 내 버전이 여기 없습니다.

  • 많이 헷갈리는 말

    공유 폴더 메모

    origin/main

    가장 헷갈리는 것. 공유 폴더 자체가 아니라, 내가 마지막으로 확인했을 때 공유 폴더가 어디까지였는지 적어둔 메모입니다. 이 메모는 내 컴퓨터에 있습니다. 동료가 새 버전을 보내도, 내가 받아오기 전까지 이 메모는 그대로입니다.

  • 원고 통째로 복사해 오기

    클론 clone

    공유 폴더을 내 컴퓨터로 처음 한 번 통째로 가져오는 것.

  • 두 작업본으로 나뉜 원고를 하나로 합치기

    머지 merge

    따로 고쳐온 두 작업본으로 나뉜 원고를 하나로 모읍니다. 편집자가 두 원고를 나란히 놓고 합치는 것과 같습니다.

  • 많이 헷갈리는 말

    같은 문장을 서로 다르게 고침

    충돌 conflict

    같은 줄을 한쪽은 A로, 다른 쪽은 B로 고쳐놓은 채 합치려 할 때 생깁니다. Git은 어느 쪽이 맞는지 알 수 없어 멈추고 편집자에게 결정을 넘깁니다. 겁먹을 일이 아닙니다. 파일을 열어 남길 쪽만 남기고 git add 한 뒤 이어가면 됩니다.

  • 잠깐 치워두기

    스태시 stash

    아직 버전 남기기 아까운 작업물을 서랍에 잠깐 넣어두는 것. 나중에 다시 꺼낼 수 있습니다.

비유는 여기까지입니다

원고 비유는 어디에 무엇이 담기는지를 잡는 데까지만 씁니다. Git이 실제로는 파일 전체를 매번 복사하지 않고 달라진 부분만 영리하게 저장하지만, 처음 배울 때 그건 몰라도 됩니다. 익숙해지면 원래 용어만 쓰게 됩니다.

명령어 사전

알파벳순이 아니라 상황순입니다. 제목 줄을 누르면 그 자리에서 펼쳐지고, 그 명령이 건드리는 칸이 그림에 강조되어 함께 나옵니다. 옵션은 짧은 형태(-m)와 긴 형태(--message)를 함께 적었습니다. 검색하면 둘 다 나오는데 같은 것인 줄 모르면 헷갈리기 때문입니다.

이 명령이 건드리는 칸입니다.

  • ✓ 안전

    처음 한 번만 해두는 설정

    git config --global push.autoSetupRemote true

    바뀌는 칸 없음 (Git 설정만 바뀝니다)

    첫 올리기에서 거의 모두가 만나는 fatal: The current branch has no upstream branch 오류를 통째로 없애줍니다. Git 2.37.0부터 쓸 수 있습니다.

    이름·메일 설정과 첫 작업본 이름 
    git config --global user.name "이름"
git config --global user.email "메일주소"
git config --global init.defaultBranch main
    • user.name, user.email — 이걸 안 해두면 첫 git commit이 거부됩니다. 남기는 버전마다 붙는 이름입니다
    • init.defaultBranch main — git init의 첫 작업본 이름을 main으로 고정합니다. 매번 -b main을 붙이지 않아도 됩니다
    • --global 은 이 컴퓨터 전체, --local 은 이 저장소만입니다
    • git config --list — 지금 설정을 전부 봅니다
  • ✓ 안전

    원고 시작하기 · 받아오기

    git init -b main

    바뀌는 칸 내 기록함(.git)이 새로 생김

    -b main을 빼면 Git 설정에 따라 첫 작업본 이름이 master가 될 수 있습니다.

    이미 있는 원고를 받아오려면 · 주소 확인
    • git clone <주소> — 공유 폴더을 내 컴퓨터로 통째로 복사해 옵니다 (처음 한 번)
    • git remote -v — 지금 어느 공유 폴더에 연결돼 있는지 봅니다 (-v = --verbose)
    • git remote add origin <주소> — 연결이 없을 때 새로 맺습니다
    • git remote set-url origin <주소> — 연결된 주소를 바꿉니다
    • --global 은 이 컴퓨터 전체 설정, --local 은 이 저장소만의 설정입니다
  • ✓ 안전

    지금 상태 확인

    git status

    바뀌는 칸 없음 (보기만 합니다)

    무엇을 하든 여기서 시작합니다. 어떤 파일이 어느 칸에 있는지 한 번에 보여줍니다.

    옵션 풀어쓰기
    • -s = --short — 짧게 요약해서 봅니다
    • -b = --branch — 지금 어느 작업본(브랜치)에 있는지 같이 보여줍니다
    • git diff — 책상과 고르는 자리의 차이
    • git diff --staged = git diff --cached — 고르는 자리와 마지막 버전의 차이. 두 이름이 같은 뜻인데 검색하면 둘 다 나옵니다
  • ✓ 안전

    이번 버전에 넣을 파일 고르기

    git add <파일>

    바뀌는 칸 책상 → 고르는 자리 (작업 폴더 → 스테이징)

    파일 10개를 고쳐도 add한 것만 그 버전에 들어갑니다.

    전부 담는 세 가지 방법 · 옵션 풀어쓰기

    git add . 과 git add -A 는 미묘하게 다릅니다.

    . 은 지금 있는 폴더와 그 아래만 담습니다. -A 는 어느 폴더에 있든 저장소 전체를 담습니다. 프로젝트 최상위에서 실행하면 결과가 같아서 차이를 못 느끼지만, 하위 폴더에서 실행하면 . 은 위쪽 폴더의 변경을 빠뜨립니다.

    • git add . — 현재 폴더와 그 아래 전부 (가장 많이 쓰는 형태)
    • -A = --all — 저장소 전체 전부
    • -u = --update — 이미 Git이 알고 있는 파일만 (새 파일 제외)
    • -p = --patch — 파일 안에서 부분만 골라 담기
  • ✓ 안전

    버전 남기기 (기록 남기기)

    git commit -m "메시지"

    바뀌는 칸 고르는 자리 → 내 기록함 (스테이징 → 로컬 main)

    내 컴퓨터의 .git 기록함에만 남습니다. GitHub에는 아무것도 가지 않습니다.

    옵션 풀어쓰기
    • -m = --message — 버전에 붙일 설명을 바로 적습니다
    • -a = --all — 고르는 단계를 건너뛰고 바뀐 것을 바로 버전으로 남깁니다 (새 파일은 제외)
    • git commit -am "메시지" — -a와 -m을 붙여 쓴 것입니다. 짧은 옵션은 이렇게 합칠 수 있습니다
    • --amend — 짧은 형태가 없습니다. 방금 남긴 버전을 고쳐 씁니다
    • --no-edit — 짧은 형태가 없습니다. 설명은 그대로 두겠다는 뜻입니다
  • ✓ 안전

    공유 폴더에 올리기

    git push

    바뀌는 칸 내 기록함 → 공유 폴더 (+ origin/main 메모 갱신)

    여기서 처음으로 인터넷이 필요합니다. 성공하면 메모도 함께 최신이 됩니다.

    옵션 풀어쓰기
    • -u = --set-upstream — “이 작업본는 앞으로 여기에 올린다”를 한 번 정해둡니다
    • -f = --force — 강제로 덮어씁니다. 동료의 버전이 사라질 수 있습니다
    • -d = --delete — 공유 폴더 쪽 작업본을 지웁니다
  • ✓ 안전

    공유 폴더 소식 받아오기

    git fetch

    바뀌는 칸 공유 폴더 → origin/main 메모

    “확인만 하는 명령”이 아닙니다. 새 버전을 실제로 내려받아 메모를 갱신합니다. 다만 내 기록함과 책상은 건드리지 않으므로 안심하고 자주 실행해도 됩니다.

    옵션 풀어쓰기
    • -p = --prune — 공유 폴더에서 사라진 작업본를 내 쪽 목록에서도 정리합니다
    • -t = --tags — 태그도 함께 받아옵니다
    • --all — 짧은 형태가 없습니다. (-a는 --append라 뜻이 다릅니다)
  • ! 주의

    받아와서 합치기

    git pull

    바뀌는 칸 메모 → 내 기록함 → 책상 (세 칸 전부)

    fetch + merge입니다. 책상까지 바뀌므로 충돌이 날 수 있습니다. 먼저 git status로 정리된 상태인지 확인하세요.

  • ! 주의

    파일 수정 취소

    git restore <파일>

    바뀌는 칸 고르는 자리 → 책상

    가져오는 기준이 HEAD가 아니라 고르는 자리(스테이징)입니다. 이 차이가 함정을 만듭니다.

    가장 많이 걸리는 함정

    git add app.js 한 뒤 git restore app.js를 실행하면 아무 일도 없는 것처럼 보입니다. 고르는 자리에 이미 담아둔 내용이 있고, restore는 거기서 가져오기 때문입니다.

    마지막 버전 상태로 되돌리려면 git restore --source=HEAD -- app.js를 쓰세요.

    • -s = --source — 어디서 가져올지 정합니다 (--source=HEAD)
    • -S = --staged — 고르는 자리를 되돌립니다 (대문자입니다)
    • -W = --worktree — 책상을 되돌립니다 (기본값)
    • -p = --patch — 부분만 골라 되돌립니다
  • ✓ 안전

    담은 것 도로 빼기

    git restore --staged <파일>

    바뀌는 칸 내 기록함(HEAD) → 고르는 자리

    고르는 자리에서만 뺍니다. 책상에서 고친 내용은 그대로 남습니다. 그래서 안전합니다.

    옵션 풀어쓰기 · 옛날 방식
    • -S = --staged — 위 명령의 짧은 형태는 git restore -S <파일>입니다
    • 검색하면 나오는 git reset HEAD <파일>과 같은 일을 합니다
  • ! 주의

    마지막 버전 상태로 파일 되돌리기

    git restore --source=HEAD -- <파일>

    바뀌는 칸 내 기록함(HEAD) → 책상

    아직 버전으로 남기지 않은 수정이 사라집니다. 되돌릴 수 없으니 git diff로 무엇이 사라지는지 먼저 보세요.

  • ✓ 안전

    다른 작업본으로 옮겨가기

    git switch <브랜치>

    바뀌는 칸 내 기록함 → 고르는 자리 + 책상

    아직 버전으로 남기지 않은 수정이 있으면 Git이 이동을 막아줍니다.

    옵션 풀어쓰기
    • -c = --create — 새 작업본를 만들면서 옮겨갑니다
    • -C = --force-create — 이미 있어도 덮어쓰며 만듭니다
    • -d = --detach — 작업본 이름 없이 특정 버전만 펼쳐 봅니다
    • git switch - — 바로 전 작업본로 돌아갑니다
  • ! 주의

    방금 남긴 버전 고쳐 쓰기

    git commit --amend

    바뀌는 칸 내 기록함 (로컬 main)

    기존 버전을 고치는 게 아니라 새 버전으로 갈아끼웁니다. 버전 번호(해시)가 바뀌므로 이미 올렸다면 강제로 덮어써야 합니다. 협업 중이라면 revert를 쓰세요.

  • ✓ 안전

    이미 보낸 버전 되돌리기

    git revert <해시>

    바뀌는 칸 내 기록함 (버전 하나 추가)

    기록을 지우지 않고 반대 내용의 버전을 하나 더 만듭니다. 그래서 동료 작업을 망치지 않습니다.

    옵션 풀어쓰기
    • -n = --no-commit — 되돌리되 버전은 아직 만들지 않습니다
    • -e = --edit — 버전 설명을 직접 씁니다
    • git log --oneline -5 의 -5 = -n 5 = --max-count=5 — 최근 5장만 봅니다

    버전을 가리키는 표기법

    HEAD 는 지금 펼친 페이지, HEAD~1 은 한 장 앞, HEAD~2 는 두 장 앞입니다. HEAD^ 는 HEAD~1 과 같은 뜻이라 검색하면 둘 다 나옵니다. 해시 대신 이 표기를 써도 됩니다.

  • ✓ 안전

    작업본를 옮기지 않고 동시에 작업하기

    git worktree add <경로> <브랜치>

    바뀌는 칸 새 책상(작업 폴더)이 하나 더 생김

    같은 원고를 다른 폴더에 동시에 펼쳐놓습니다. 작업 중 급한 수정이 들어왔을 때 지금 것을 버전을 남겨두지 않고도 별도 폴더에서 고칠 수 있습니다.

    사용법과 주의점 
    git worktree add ../프로젝트-hotfix hotfix
git worktree list
git worktree remove ../프로젝트-hotfix

    같은 작업본를 두 폴더에서 동시에 열 수 없습니다. 이 제약을 모르면 오류 메시지를 이해할 수 없습니다.

    stash와의 차이 — stash는 한 폴더 안에서 작업을 서랍에 치워두는 것이고, worktree는 폴더를 하나 더 만드는 것입니다.

  • ✓ 안전

    작업을 잠깐 치워두기

    git stash

    바뀌는 칸 책상 + 고르는 자리 → 서랍

    고치던 것을 버전으로 남기기는 애매한데 잠깐 치워야 할 때 씁니다. 책상이 마지막 버전 상태로 깨끗해집니다.

    꺼내기 · 새 파일 함정
    • git stash = git stash push — 그냥 stash는 push를 생략한 것입니다
    • git stash pop — 꺼내면서 서랍에서 지웁니다
    • git stash apply — 꺼내되 서랍에 그대로 둡니다
    • git stash list — 서랍에 무엇이 있는지 봅니다

    아직 한 번도 담은 적 없는 새 파일은 치워지지 않습니다. -u = --include-untracked 를 붙여야 새 파일도 함께 들어갑니다. 이걸 모르면 치웠다고 생각한 파일이 책상에 그대로 남아 있습니다.

  • ! 주의

    작업본 목록 보기 · 지우기

    git branch -a

    바뀌는 칸 보기는 없음 · 지우기는 내 기록함

    -a = --all — 공유 폴더 쪽 작업본까지 함께 봅니다.

    지울 때 대문자와 소문자가 다릅니다
    • -d = --delete — 합쳐진 작업본만 지웁니다. 안 합쳐졌으면 Git이 막아줍니다
    • -D = --delete --force — 확인 없이 강제로 지웁니다
    • -m = --move — 작업본 이름을 바꿉니다

    대문자 -D가 막아주는 장치를 끕니다. 아직 합치지 않은 작업본을 -D로 지우면 그 작업본에만 있던 버전은 목록에서 사라집니다. 바로 뒤라면 git reflog로 되찾을 수 있습니다.

  • ✓ 안전

    내 기록함과 공유 폴더 비교하기

    git log --oneline origin/main..main

    바뀌는 칸 없음 (보기만 합니다)

    내게는 있고 공유 폴더에는 없는 버전, 즉 아직 안 보낸 것을 보여줍니다.

    반대 방향과 가장 큰 함정 
    git log --oneline origin/main..main   # 내게는 있고 공유 폴더에 없는 버전
git log --oneline main..origin/main   # 공유 폴더에는 있고 내게 없는 버전

    공유 폴더의 지금 상태와 비교하는 것이 아닙니다. 내 컴퓨터에 있는 메모(origin/main)와 비교합니다. 동료가 방금 올린 것은 이 메모에 없으므로 여기에도 안 나옵니다.

    최신으로 비교하려면 git fetch로 메모부터 갱신하세요.

  • ✓ 안전

    원고 기록을 그림으로 보기

    git log --oneline --graph --all

    바뀌는 칸 없음 (보기만 합니다)

    작업본이 어디서 갈라지고 어디서 합쳐졌는지 선으로 그려줍니다. 말로 설명하기 어려운 상태를 볼 때 가장 빠릅니다.

    옵션 풀어쓰기
    • --oneline — 버전 하나를 한 줄로 줄여 보여줍니다
    • --graph — 갈라지고 합쳐진 모양을 선으로 그립니다
    • --all — 지금 작업본만이 아니라 전부 보여줍니다
    • 세 옵션 모두 짧은 형태가 없습니다. 검색해도 -o 같은 것은 나오지 않습니다
  • ✓ 안전

    지워진 버전 찾기 (최후의 수단)

    git reflog

    바뀌는 칸 없음 (보기만 합니다)

    내가 지금까지 어디에 있었는지 전부 적힌 이동 기록입니다. 사라진 것 같은 버전의 주소를 여기서 찾습니다.

    어디까지 구해주나요 
    git reflog
git switch -c 되살리기 <찾은주소>

    구해줍니다 — 옮겨지거나 지워진 버전. 되돌리기를 잘못했거나 작업본을 강제로 지운 경우가 여기입니다.

    못 구합니다 — 한 번도 버전으로 남기지 않은 수정. 버전이 된 적 없으면 기록 자체가 없습니다.

    그래서 위험한 명령 전에 먼저 버전을 남기거나 git stash로 치워두는 것이 중요합니다.

옛날 명령어 → 지금 권장 명령어

검색하면 대부분 checkout 기준의 옛날 답변이 나옵니다. 부정하지 말고, 같은 일을 한다는 것만 알아두세요.

옛날 명령어와 현재 권장 명령어 대응표
하고 싶은 일권장 (현재)검색에서 자주 보이는 방식
고르는 자리 내용으로 파일 되돌리기git restore <파일>git checkout -- <파일>
담은 것 빼기git restore --staged <파일>git reset HEAD <파일>
작업본 옮기기git switch <브랜치>git checkout <브랜치>
작업본 만들고 옮기기git switch -c <브랜치>git checkout -b <브랜치>
바로 전 작업본로git switch -git checkout -

checkout 하나가 “작업본 옮기기”와 “파일 되돌리기”라는 전혀 다른 일을 담당했던 것이 혼란의 큰 원인이었습니다. switch와 restore는 2019년 도입 후 오랫동안 실험 상태였다가 2025년에 정식이 되었고, 그래서 기존 자료 대부분이 아직 checkout 기준입니다.
