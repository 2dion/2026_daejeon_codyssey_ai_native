### 1.2 Pro Git이 충실히 다루는 것 (재작성 불필요)

- 3영역 모델(작업 디렉토리 / 스테이징 / 저장소)과 기본 커밋 흐름
- 브랜치의 실체가 커밋을 가리키는 포인터라는 설명
- Merge와 Rebase의 차이, 충돌 해결
- 리모트 브랜치, 추적(tracking) 브랜치 개념
- Reset의 세 단계(`--soft` / `--mixed` / `--hard`)
- reflog를 통한 복구
- Stash, 태그, Alias
- Git 내부 구조(객체, refs, packfile)

**결론: 개념의 뼈대는 Pro Git으로 충분하다.** 우리 서비스가 채워야 할 것은 개념이 아니라 (a) 시각화 (b) 최신 명령어 (c) 상황 → 명령어 매핑이다.

### 1.3 채워야 할 공백

| 우선순위 | 항목 | 이유 |
|---|---|---|
| 높음 | `git switch` / `git restore` | 초보자에게 `checkout`보다 먼저 가르쳐야 함 |
| 높음 | 기본 브랜치 `main` | GitHub 신규 저장소 기본값이 `main`인데 책은 `master` 기준 |
| 높음 | `git init -b main` | 로컬에서 시작할 때 브랜치 이름 지정 |
| 중간 | `push.autoSetupRemote` | 초보자가 가장 많이 만나는 에러 중 하나를 원천 제거 |
| 중간 | `git worktree` | 브랜치 전환 없이 여러 작업을 병행하는 방법 |
| 낮음 | `git maintenance`, `sparse-checkout`, partial clone | 대용량 저장소용. 타겟 사용자와 무관 |
| 낮음 | Git LFS | 필요해지면 검색하면 됨 |

`git switch` / `git restore`는 2019년 v2.23에 도입됐으나 오랫동안 experimental 표시가 붙어 있었고, `restore`는 2025년 8월 v2.51에서 정식이 되었다. Pro Git이 빌드된 2023년 시점에는 소개하기 애매한 상태였기 때문에 누락된 것으로 보인다. 지금 초보자를 가르친다면 반드시 포함해야 한다.

## 2. 핵심 학습 모델

이 서비스의 모든 설명은 **네 개의 영역과 하나의 경계**로 환원된다.

```
┌─ 내 컴퓨터 (로컬) ──────────────┐
│                                  │
│   작업 폴더                       │
│      ↓ git add                    │
│   스테이징 영역                    │
│      ↓ git commit                 │
│   로컬 저장소 (.git)               │
│                                  │
└──────────┬───────────────────────┘
           ↓ git push / ↑ git fetch
     원격 저장소 (GitHub)
```

### 2.1 초보자가 이 모델에서 반드시 얻어야 할 세 가지

**1) 커밋은 GitHub에 아무것도 보내지 않는다.**

가장 흔한 오해다. `git commit`은 내 컴퓨터의 `.git` 폴더에 기록을 남길 뿐이며, 인터넷이 끊겨 있어도 동작한다. GitHub에 반영되는 것은 오직 `git push` 뿐이다.

**2) GitHub 화면에서 본 것은 내 컴퓨터에 자동으로 오지 않는다.**

웹에서 파일을 수정하거나 팀원이 push한 내용은 `git pull`(또는 `git fetch`) 전까지 내 폴더에 존재하지 않는다.

**3) 스테이징은 "이번 커밋에 담을 목록"이다.**

작업 폴더에서 파일 10개를 고쳤어도 `git add`한 3개만 커밋된다. 이 선택 단계가 있다는 것이 Git과 단순 백업의 결정적 차이다.

### 2.2 각 영역을 눈으로 확인하는 명령어

| 알고 싶은 것 | 명령어 |
|---|---|
| 지금 네 영역이 어떤 상태인가 | `git status` |
| 작업 폴더 ↔ 스테이징 차이 | `git diff` |
| 스테이징 ↔ 마지막 커밋 차이 | `git diff --staged` |
| 로컬 저장소의 커밋 기록 | `git log --oneline --graph --all` |
| 원격이 어디에 연결돼 있나 | `git remote -v` |
| 로컬과 원격 중 어느 쪽이 앞서 있나 | `git status` 또는 `git log --oneline origin/main..main` |

`git status`는 이 서비스에서 **모든 답변의 첫 단계로 고정 제시한다.** 사고가 났을 때 무엇을 하든 현재 상태 확인이 먼저다. AI 응답 프롬프트에도 이 규칙을 넣는다.

## 3. 시각화 설계

### 3.1 시각화 목록과 우선순위

| # | 시각화 | 배치 섹션 | 형태 | 우선순위 |
|---|---|---|---|---|
| V1 | 네 영역 + 로컬/원격 경계 | Git 3분 개념 | 고정 SVG | **필수** |
| V2 | 커밋 그래프 before/after | 사고 수습 (AI 결과) | 동적 SVG | **필수** |
| V3 | 명령어별 영향 범위 하이라이트 | 명령어 사전 | 고정 SVG + JS | 권장 |
| V4 | 브랜치 분기와 병합 | Git 3분 개념 | 고정 SVG | 선택 |
| V5 | worktree 구조 | 명령어 사전 | 고정 SVG | 선택 |

V1과 V2만으로도 과제 요구사항은 충족된다. V3 이하는 시간이 남을 때 추가한다.

### 3.2 V1 — 네 영역 다이어그램 (고정)

서비스의 기준점. 세로 4단 배치에 로컬 영역을 점선 박스로 묶고, 원격만 밖에 둔다. 세로 배치를 택한 이유는 모바일에서 가로 스크롤 없이 그대로 읽히기 때문이다.

**구성 요소**

- 박스 4개 (작업 폴더 / 스테이징 영역 / 로컬 저장소 / 원격 저장소)
- 점선 컨테이너 1개 ("내 컴퓨터") — 앞의 세 박스를 감쌈
- 아래 방향 화살표 3개 (`git add`, `git commit`, `git push`)
- 위 방향 화살표 2개 (`git restore --staged`, `git fetch`)
- 로컬 박스는 청록 계열, 원격 박스는 보라 계열로 구분

**인터랙션 (선택)** — 명령어 라벨에 마우스를 올리면 해당 화살표와 양쪽 박스가 강조되고, 하단에 한 줄 설명이 나온다. CSS `:hover`만으로 구현 가능하므로 비용이 낮다.

### 3.3 V2 — 커밋 그래프 (동적)

AI 응답의 `before` / `after` 배열을 받아 렌더링한다. 상세 명세는 기획서 3.5절 참조.

**렌더링 함수 시그니처**

```javascript
// nodes: [{ id, parent, label, highlight }]
// container: SVG를 삽입할 DOM 요소
function renderGraph(nodes, container) { ... }
```

**좌표 계산 규칙**

```
반지름        r  = 13
원 간격       gap = 110
시작 x        x0 = 40
중심 y         y = 60
i번째 원의 x  = x0 + i * gap
연결선        (x0 + i*gap + r, y) → (x0 + (i+1)*gap - r, y)
라벨 알약      원 중심 위 y - 34, 폭은 글자수 * 8 + 20
SVG 폭        x0 * 2 + (n-1) * gap + r * 2
```

브랜치가 2개인 경우 두 번째 브랜치는 `y = 60 + 70`에 배치하고, 분기점에서 곡선(`Q` 커맨드) 하나로 잇는다.

**제한** — 커밋 7개, 브랜치 2개, 애니메이션 없음.

### 3.4 V3 — 명령어별 영향 범위 (권장)

V1과 동일한 SVG를 재사용한다. 명령어 사전 카드를 클릭하면 V1 다이어그램에서 그 명령이 건드리는 영역만 색이 진해지고 나머지는 흐려진다.

| 명령어 | 영향 범위 |
|---|---|
| `git add` | 작업 폴더 → 스테이징 |
| `git commit` | 스테이징 → 로컬 저장소 |
| `git push` | 로컬 저장소 → 원격 |
| `git fetch` | 원격 → 로컬 저장소 |
| `git pull` | 원격 → 로컬 저장소 → 작업 폴더 (세 영역 전부) |
| `git restore <파일>` | 로컬 저장소 → 작업 폴더 (덮어씀) |
| `git restore --staged` | 스테이징만 되돌림 |
| `git reset --hard` | 세 영역 전부 덮어씀 (**되돌릴 수 없음**) |

이 표 자체가 명령어 사전 섹션의 핵심 콘텐츠가 된다. "이 명령이 어느 영역을 건드리는가"를 명시하는 자료는 의외로 드물다.

## 4. 상황별 터미널 명령어

명령어 사전 섹션과 AI 프롬프트의 참고 자료로 사용한다. **명령어를 알파벳순이 아니라 상황순으로 배열하는 것이 이 서비스의 차별점이다.**

### 4.1 시작하기

| 상황 | 명령어 |
|---|---|
| 내 폴더에서 Git 시작 | `git init -b main` |
| GitHub 저장소를 내려받기 | `git clone <URL>` |
| 원격 주소 연결 | `git remote add origin <URL>` |
| 원격 주소 확인 | `git remote -v` |
| 원격 주소 변경 | `git remote set-url origin <URL>` |

`git init`만 쓰면 Git 설정에 따라 기본 브랜치가 `master`가 될 수 있다. `-b main`을 붙이거나, 한 번만 `git config --global init.defaultBranch main`을 설정해두면 이후로는 신경 쓸 필요가 없다.

### 4.2 매일 쓰는 흐름

```bash
git status                    # 항상 여기서 시작
git add <파일>                 # 특정 파일만
git add .                     # 현재 폴더 전부
git commit -m "메시지"
git push
```

첫 push에서 `fatal: The current branch has no upstream branch` 에러를 만난다면 `git push -u origin main`으로 한 번 연결해주면 된다. 매번 겪기 싫다면 아래를 한 번만 설정한다.

```bash
git config --global push.autoSetupRemote true
```

이 설정은 Git 2.37.0부터 사용할 수 있으며, 추적 대상이 없는 브랜치를 push할 때 자동으로 `--set-upstream`을 적용한다. **초보자가 가장 자주 만나는 에러 하나를 통째로 없애주므로, "Git 3분 개념" 섹션의 마무리로 안내하기 좋다.**

### 4.3 되돌리기 (구식 명령 → 권장 명령)

Pro Git은 `checkout`과 `reset` 위주로 설명하지만, 지금은 목적별로 나뉜 명령을 쓰는 편이 훨씬 안전하고 이해하기 쉽다.

| 하고 싶은 일 | 권장 (현재) | 예전 방식 |
|---|---|---|
| 파일 수정을 버리고 마지막 커밋 상태로 | `git restore <파일>` | `git checkout -- <파일>` |
| `add`한 것을 스테이징에서만 내리기 | `git restore --staged <파일>` | `git reset HEAD <파일>` |
| 브랜치 이동 | `git switch <브랜치>` | `git checkout <브랜치>` |
| 새 브랜치 만들고 이동 | `git switch -c <브랜치>` | `git checkout -b <브랜치>` |
| 직전 브랜치로 돌아가기 | `git switch -` | `git checkout -` |

`checkout` 하나가 "브랜치 이동"과 "파일 되돌리기"라는 전혀 다른 두 가지 일을 모두 담당했던 것이 초보자 혼란의 큰 원인이었다. **명령어 사전에서 이 대응표를 나란히 보여주면, 검색으로 나온 옛날 답변을 만나도 해석할 수 있게 된다.**

### 4.4 커밋 수정

| 상황 | 명령어 | 위험도 |
|---|---|---|
| 직전 커밋 메시지만 고치기 | `git commit --amend -m "새 메시지"` | 주의 |
| 직전 커밋에 파일 추가 | `git add <파일>` 후 `git commit --amend --no-edit` | 주의 |
| 커밋을 취소하되 변경 내용은 유지 | `git reset --soft HEAD~1` | 주의 |
| 이미 push한 커밋을 안전하게 되돌리기 | `git revert <커밋해시>` | 안전 |
| 커밋과 변경 내용을 모두 버리기 | `git reset --hard HEAD~1` | **위험** |

`--amend`와 `reset`은 이미 push한 커밋에 쓰면 강제 푸시가 필요해지고, 협업 중이라면 팀원의 작업을 망칠 수 있다. **이미 원격에 올라간 것은 `revert`로 처리한다**는 원칙을 서비스 전체에서 일관되게 안내한다.

### 4.5 위험한 명령과 백업

되돌릴 수 없는 명령을 실행하기 전에는 항상 백업 브랜치를 만든다.

```bash
git branch backup-$(date +%Y%m%d-%H%M%S)
```

작업이 사라진 것 같을 때는 대부분 reflog에 남아 있다.

```bash
git reflog                  # 최근 HEAD가 거쳐온 위치 목록
git reset --hard <해시>      # 원하는 시점으로 복구
```

**reflog는 이 서비스에서 가장 강조해야 할 안전망이다.** 초보자는 `reset --hard` 후 작업이 영영 사라졌다고 생각하고 포기하는데, 대부분 복구할 수 있다는 사실을 아는 것만으로 심리적 부담이 크게 줄어든다.

### 4.6 로컬과 원격의 차이 확인

| 알고 싶은 것 | 명령어 |
|---|---|
| 원격에 새 커밋이 있는지 확인만 (내 파일은 안 건드림) | `git fetch` |
| 원격 내용을 가져와 합치기 | `git pull` |
| 원격에는 있고 나에게 없는 커밋 | `git log --oneline main..origin/main` |
| 나에게는 있고 원격에 없는 커밋 | `git log --oneline origin/main..main` |

`fetch`와 `pull`의 차이는 이 서비스의 핵심 설명 대상이다. **`fetch`는 확인만, `pull`은 확인 후 내 파일까지 변경**한다. V1 다이어그램에서 `fetch`는 원격 → 로컬 저장소까지만 화살표가 오고, `pull`은 작업 폴더까지 이어지는 것으로 표현한다.

### 4.7 worktree (Pro Git 미수록)

브랜치를 전환하려면 보통 작업 중인 내용을 커밋하거나 stash해야 한다. worktree는 **같은 저장소를 다른 폴더에 동시에 펼쳐놓는** 기능으로, 이 과정 없이 두 브랜치를 병행할 수 있다.

```bash
git worktree add ../프로젝트-hotfix hotfix   # 새 폴더에 hotfix 브랜치를 펼침
git worktree list                            # 현재 펼쳐진 목록
git worktree remove ../프로젝트-hotfix        # 정리
```

**타겟 사용자에게 필요한 상황** — 기능을 개발하던 중 급한 버그 수정 요청이 들어왔을 때, 지금 작업을 커밋하지 않고도 별도 폴더에서 수정하고 push할 수 있다.

주의할 점은 **같은 브랜치를 두 worktree에서 동시에 열 수 없다**는 것이다. 이 제약을 모르면 에러 메시지를 이해하지 못한다.

`stash`와의 차이도 함께 설명한다. `stash`는 작업을 잠시 치워두는 것(한 폴더)이고, worktree는 폴더를 하나 더 만드는 것이다. 에디터를 두 개 띄워놓고 비교하며 작업할 수 있다는 점이 다르다.

## 5. 콘텐츠 작성 원칙

1. **명령어보다 상황을 먼저 쓴다.** 제목은 "reset 명령"이 아니라 "커밋을 잘못했을 때"로 단다.
2. **영역을 항상 명시한다.** 모든 명령어 설명에 "이 명령은 어느 영역에서 어느 영역으로 옮기는가"를 한 줄 넣는다.
3. **되돌릴 수 있는지 먼저 말한다.** 위험도 배지를 명령어보다 위에 배치한다.
4. **옛날 명령어를 부정하지 않는다.** 검색하면 `checkout`이 나오므로, 대응표로 해석할 수 있게 해준다.
5. **한 화면에 한 개념.** 스크롤 없이 읽히는 분량으로 자른다.
