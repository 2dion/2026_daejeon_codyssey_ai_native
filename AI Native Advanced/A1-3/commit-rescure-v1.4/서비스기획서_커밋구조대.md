## 1. 서비스 개요

### 1.1 문제 정의

Git 입문자의 어려움은 "명령어를 모르는 것"이 아니라 **"내 상황에 어떤 명령어를 써야 하는지, 그리고 그 명령이 무엇을 바꾸는지 모르는 것"** 이다.

- 검색어를 만들 수 없다. "커밋을 잘못했어요"를 어떤 용어로 검색해야 하는지 모른다.
- 검색 결과 대부분이 옛날 명령어(`checkout`, `reset`) 기준이라, 지금 권장되는 `switch` / `restore`와 같은 일을 한다는 것조차 모른다.
- 명령어를 실행했는데 무슨 일이 일어난 건지 모른다. **내 컴퓨터가 바뀐 것인지, GitHub이 바뀐 것인지 구분하지 못한다.**
- 되돌릴 수 없는 명령을 실행해 작업 내용을 잃는다. 무엇을 잃게 되는지 미리 알 방법이 없다.

마지막 두 가지가 사고의 근본 원인이다. **"이 명령이 어느 영역을 건드리고, 무엇을 잃게 되는가"** 를 모른 채 실행하기 때문이다.

### 1.2 서비스 목적

사용자가 겪은 상황을 평소 쓰는 말 그대로 입력하면,

1. 무슨 일이 일어난 것인지 한 줄로 정리하고
2. **확인된 사실과 추정을 구분해서** 보여주고
3. 수습 명령어를 단계별로, 각 줄의 설명과 함께 제시하고
4. 각 명령이 **바꾸는 영역과 바꾸지 않는 영역**을 표시하고
5. 위험한 명령이면 **무엇을 잃게 되는지 먼저 확인시킨다**

목표는 "명령어를 알려주는 것"이 아니라 **"실행하기 전에 무슨 일이 일어날지 이해시키는 것"** 이다.

### 1.3 타겟 사용자

| 구분 | 내용 |
|---|---|
| 주 타겟 | Git을 배운 지 3개월 이내이면서 개인 프로젝트에 실제로 쓰고 있는 사람 |
| 구체적 상황 | 부트캠프 수강생, 비전공 학습자, 팀 프로젝트에서 처음 협업하는 대학생 |
| 부 타겟 | Git을 쓰긴 하지만 add / commit / push 세 가지만 반복해온 사람 |
| 제외 대상 | rebase, cherry-pick, reflog를 자유롭게 쓰는 숙련자 |

### 1.4 제공 가치

- **검색 시간 단축**: 용어를 몰라도 상황 설명만으로 답을 얻는다
- **사고 예방**: 위험한 명령 실행 전에 잃게 될 것을 확인한다
- **최신 기준 학습**: 검색으로 나오는 옛날 명령어를 해석할 수 있게 된다
- **정확한 모델**: 로컬 `main`과 `origin/main`, GitHub `main`이 다르다는 것을 이해한다

**Oh Shit, Git!?!** 은 목적이 가장 가깝다. "문제를 고치려면 그 문제의 이름을 이미 알아야 검색이 된다"는 인식에서 출발했고, 한국어판(`ohshitgit.com/ko`)도 있다. 다만 목록에 없는 상황은 대응하지 못한다.

**시각화 도구군**(learnGitBranching, Visualizing Git, A Grip On Git, LearnGit.io)은 모두 사용자가 명령어를 이미 안다는 전제에서 출발한다.

### 2.3 섹션 2 — Git 3분 개념

**이 섹션은 서비스 전체의 기준점이다.** 이후 모든 설명이 여기서 정의한 영역 용어를 사용한다.

**5영역 모델**

```
┌─ 내 컴퓨터 (로컬) ────────────────────────┐
│   ① 작업 폴더                              │
│        ↕                                   │
│   ② 스테이징 영역 (index)                   │
│        ↕                                   │
│   ③ 로컬 저장소 (.git)                      │
│        ├── main          내 커밋 기록        │
│        └── origin/main   마지막 fetch에서    │
│                          본 GitHub의 상태    │
└────────────────┬──────────────────────────┘
                 ↕ 네트워크
   ④ GitHub의 main   ← 실제 원격 상태
```

**전달해야 할 네 가지 사실**

1. `git commit`은 GitHub에 아무것도 보내지 않는다. 인터넷이 끊겨도 동작한다. GitHub에 반영되는 것은 `git push` 뿐이다.
2. `git add`한 파일과 작업 폴더의 파일은 **서로 다른 버전일 수 있다.** 그래서 스테이징을 별도 영역으로 본다.
3. **`origin/main`은 GitHub에 있는 것이 아니라 내 컴퓨터에 있다.** 마지막으로 `fetch`했을 때 본 GitHub의 상태를 적어둔 메모다. 동료가 GitHub에 push해도, 내가 `fetch`하기 전까지 `origin/main`은 움직이지 않는다.
4. `git fetch`는 원격의 커밋과 브랜치 정보를 **로컬 저장소로 받아와 `origin/main`을 갱신한다.** 로컬 `main`과 작업 파일에는 자동으로 합치지 않는다. (합치는 것은 `merge`이며, `pull`은 `fetch` + `merge`다.)

3번이 이 서비스에서 가장 중요한 설명이다. 초보자가 `fetch`와 `pull`을 구분하지 못하는 근본 원인이 여기에 있다.

**설명 분량 제한** — 각 항목당 두 문장 이내. 이 섹션은 읽는 곳이 아니라 보는 곳이다.

**마무리 안내**

```bash
git config --global init.defaultBranch main
git config --global push.autoSetupRemote true
```

### 2.4 섹션 3 — 사고 수습 (정적 카드 + AI 하이브리드)

**AI만 쓰지 않는다.** 자주 나오는 상황 8개는 미리 검수한 정적 카드로 즉시 보여주고, 목록에 없는 상황만 AI로 넘긴다.

```
┌──────────────────────────────────┐
│  흔한 상황은 아래에서 바로 찾으세요   │
│  [커밋에 파일 빠뜨림] [add 취소] ... │  ← 정적 카드 8개
├──────────────────────────────────┤
│  목록에 없나요? 상황을 적어주세요.     │
│  [                             ]  │  ← AI 입력 폼
└──────────────────────────────────┘
```

**정적 카드 8종**

| # | 상황 | 그래프 템플릿 |
|---|---|---|
| 1 | 커밋했는데 파일을 빼먹었다 | `amend-add-file` |
| 2 | 커밋 메시지를 잘못 썼다 | `amend-message` |
| 3 | `add`를 취소하고 싶다 | `restore-staged` |
| 4 | 파일 수정을 되돌리고 싶다 | `restore-worktree` |
| 5 | 이미 push한 커밋을 되돌리고 싶다 | `revert-pushed` |
| 6 | push가 거절됐다 (non-fast-forward) | `non-fast-forward` |
| 7 | `.env` 같은 파일을 올려버렸다 | `remove-secret` |
| 8 | 다른 브랜치에서 작업하고 있었다 | `wrong-branch` |

v1.3의 12개에서 8개로 줄였다. **Git 답변은 틀리면 사용자가 데이터를 잃으므로, 개수보다 검수 품질이 우선이다.** 각 카드는 실제 저장소에서 명령을 실행해 결과를 확인한 뒤 확정한다.

정적 카드는 AI 응답과 **동일한 JSON 구조**로 `js/presets.js`에 둔다. 렌더링 코드를 그대로 재사용한다.

**이 설계가 해결하는 세 가지**

| 문제 | 해결 |
|---|---|
| Oh Shit, Git!?!의 강점(즉답, 검증된 답) | 정적 카드로 흡수 |
| Oh Shit, Git!?!의 약점(목록에 없으면 끝) | AI로 보완 |
| Gemini 무료 할당량 소모 | 흔한 질문이 API를 소모하지 않음 |

### 2.5 섹션 4 — 명령어 사전

명령어를 알파벳순이 아니라 **상황순**으로 배열한다. 각 카드에 위험도 배지, 영향 영역, 한 줄 설명, "내 상황에 맞게 설명해줘" 버튼을 둔다.

**수록 명령어 13개**

| # | 상황 | 명령어 | 영향 영역 | 위험도 |
|---|---|---|---|---|
| 1 | 지금 상태 확인 | `git status` | 없음 (조회만) | 안전 |
| 2 | 커밋에 담을 파일 고르기 | `git add <파일>` | 작업 폴더 → 스테이징 | 안전 |
| 3 | 기록 남기기 | `git commit -m "메시지"` | 스테이징 → 로컬 `main` | 안전 |
| 4 | GitHub에 올리기 | `git push` | 로컬 `main` → GitHub `main` (+ `origin/main` 갱신) | 안전 |
| 5 | 원격 정보 받아오기 | `git fetch` | GitHub → 로컬 저장소 + `origin/main` | 안전 |
| 6 | 원격 내용 가져와 합치기 | `git pull` | `fetch` 후 `origin/main` → 로컬 `main` → 작업 폴더 | 주의 |
| 7 | **파일 수정 취소** | `git restore <파일>` | **스테이징 → 작업 폴더** | 주의 |
| 8 | `add` 취소 | `git restore --staged <파일>` | 로컬 `main`(HEAD) → 스테이징 | 안전 |
| 9 | 마지막 커밋 상태로 파일 되돌리기 | `git restore --source=HEAD -- <파일>` | 로컬 `main`(HEAD) → 작업 폴더 | 주의 |
| 10 | 브랜치 이동 | `git switch <브랜치>` | 로컬 저장소 → 스테이징 + 작업 폴더 | 안전 |
| 11 | 직전 커밋 수정 | `git commit --amend` | 로컬 `main` | 주의 |
| 12 | 이미 올린 커밋 되돌리기 | `git revert <해시>` | 로컬 `main` (새 커밋 추가) | 안전 |
| 13 | 브랜치 전환 없이 병행 작업 | `git worktree add <경로> <브랜치>` | 새 작업 폴더 생성 | 안전 |

**7번이 v1.4의 핵심 정정이다.** `git restore <파일>`의 기본 소스는 HEAD가 아니라 **index(스테이징 영역)** 다. 이 차이가 만드는 함정을 카드 본문에 반드시 적는다.

> `git add app.js`를 한 뒤 `git restore app.js`를 실행하면 아무 일도 일어나지 않은 것처럼 보입니다.
> 스테이징에 이미 `add`한 내용이 들어 있고, `restore`는 거기서 가져오기 때문입니다.
> 마지막 커밋 상태로 되돌리려면 `git restore --source=HEAD -- app.js`를 쓰세요.

**5번 `fetch`도 정정했다.** "확인만 한다"는 표현을 쓰지 않는다. fetch는 원격의 커밋 객체를 실제로 내려받아 `origin/main`을 갱신한다. 다만 로컬 `main`과 작업 파일은 건드리지 않는다.

**로컬과 원격 비교 명령의 주의사항** — 사전에 별도 항목으로 표기한다.

```bash
git log --oneline origin/main..main   # 내게는 있고 원격에 없는 커밋
git log --oneline main..origin/main   # 원격에는 있고 내게 없는 커밋
```

> 이 명령은 **GitHub의 현재 상태가 아니라 마지막 `fetch` 결과와 비교**합니다.
> 최신 상태로 비교하려면 `git fetch`를 먼저 실행하세요.

**구식 / 신식 대응표**

| 하고 싶은 일 | 권장 (현재) | 검색에서 자주 보이는 방식 |
|---|---|---|
| 스테이징 내용으로 파일 되돌리기 | `git restore <파일>` | `git checkout -- <파일>` |
| `add` 취소 | `git restore --staged <파일>` | `git reset HEAD <파일>` |
| 브랜치 이동 | `git switch <브랜치>` | `git checkout <브랜치>` |
| 브랜치 생성 후 이동 | `git switch -c <브랜치>` | `git checkout -b <브랜치>` |

`checkout` 하나가 "브랜치 이동"과 "파일 되돌리기"라는 전혀 다른 일을 담당했던 것이 초보자 혼란의 큰 원인이었다. `switch`와 `restore`는 2019년 도입 후 오랫동안 실험적 상태였다가 2025년 정식이 되었으며, 이 때문에 기존 자료 대부분이 아직 `checkout` 기준으로 쓰여 있다.

**`git worktree` (13번)** — Pro Git 2판에 수록되지 않은 개념이라 한국어 자료가 특히 적다.

```bash
git worktree add ../프로젝트-hotfix hotfix
git worktree list
git worktree remove ../프로젝트-hotfix
```

카드 설명에 두 가지를 반드시 포함한다. **같은 브랜치를 두 worktree에서 동시에 열 수 없다**는 제약, 그리고 **`stash`와의 차이**(stash는 한 폴더 안에서 작업을 치워두는 것, worktree는 폴더를 하나 더 만드는 것).

### 2.6 섹션 5 — 자주 하는 실수

제작자가 이 미션을 진행하며 실제로 겪은 사고를 기록한다. `.env`를 커밋했다가 발견한 일, 첫 push에서 upstream 에러를 만난 일, 로컬에서는 되는데 배포하면 안 되던 일 등.

템플릿 복제가 원천적으로 불가능한 영역이며, 서비스의 신뢰도를 만드는 부분이다. **개발 시작 시점부터 사고 기록을 별도 메모에 쌓아둔다.**

## 3. AI 기능 설계

### 3.1 기능 정의

| 항목 | 내용 |
|---|---|
| 기능명 | 상황 기반 Git 수습 계획 생성 |
| 입력 | 상황 설명(필수) + 보조 정보 5종(선택) + 설명 수준 |
| 출력 | 상황 요약, 근거 구분, 위험도, 단계별 명령어, 변경/유지 영역, 그래프 템플릿 ID |
| 사용 모델 | Google Gemini (Flash 계열) |
| 호출 경로 | 프론트엔드 → `/api/rescue` (Vercel Serverless Function, Python) → Gemini API |

### 3.2 AI를 사용하는 이유

정형화된 질문 8개는 정적 카드로 대응한다. AI가 필요한 것은 다음 같은 입력이다.

> "어제 만든 브랜치에서 작업하다가 실수로 main에 머지했는데, 그 전에 커밋 하나를 빼먹은 것 같아요"

브랜치 생성 시점, 머지 여부, 누락된 커밋이라는 세 조건이 얽혀 있다. 조합은 사실상 무한하며 규칙 기반 분기로 대응할 수 없다.

### 3.3 입력 UI 명세

v1.3까지는 textarea 하나였으나, 그 정보만으로는 **이미 push했는지, 현재 브랜치가 무엇인지, 변경이 staged 상태인지** 판단할 수 없다. AI가 이를 추측하면 틀린 명령어가 나온다. 따라서 보조 필드를 추가한다.

| 필드 | 필수 | 형태 | 제한 |
|---|:---:|---|---|
| 어떤 상황인가요 | **예** | textarea | 5~1,000자 |
| 실행한 명령 | 아니요 | input | 300자 |
| 오류 메시지 | 아니요 | textarea | 1,000자 |
| `git status` 결과 | 아니요 | textarea | 1,000자 |
| 이미 push했나요 | 아니요 | 라디오 | 예 / 아니요 / 모르겠음(기본) |
| 설명 수준 | 아니요 | 라디오 | 완전 처음(기본) / 기본은 알아요 |

**선택 필드는 접힘(details) 상태로 두고 "더 정확한 답을 원하면 열어주세요"로 안내한다.** 필수 항목이 늘어나면 초보자가 이탈한다. 다만 채울수록 답이 정확해진다는 점을 명시해, 무엇이 중요한 정보인지 학습되게 한다.

입력창 하단에 상시 노출한다.

> 비밀번호, API 키, 액세스 토큰, 비공개 저장소 주소가 포함되지 않았는지 확인해주세요.

### 3.4 AI가 지켜야 할 규칙

시스템 프롬프트에 명시한다. **이것이 서비스 품질을 결정한다.**

1. **첫 단계는 항상 `git status`다.** 사용자가 상황을 잘못 설명했을 가능성을 이 단계가 걸러준다.
2. **`checkout`이 아니라 `switch` / `restore`를 제시한다.**
3. **기본 브랜치는 `main`으로 가정한다.** 사용자가 `master`라고 명시한 경우만 예외.
4. **이미 원격에 올라간 커밋은 `revert`로 처리한다.** `push` 여부가 `모르겠음`이면 확인 방법을 먼저 안내하고, 확정 전에는 되돌릴 수 없는 명령을 제안하지 않는다.
5. **각 명령마다 변경 영역과 유지 영역을 모두 명시한다.** "무엇이 바뀌지 않는가"가 초보자에게는 더 중요한 정보다.
6. **확인된 사실과 추정을 구분한다.** 사용자가 입력하지 않은 정보는 절대 확정으로 서술하지 않는다.
7. **커밋 ID나 그래프를 직접 만들지 않는다.** 그래프가 필요하면 정해진 템플릿 목록에서 하나를 고른다. 맞는 것이 없으면 `none`을 반환한다.

6번과 7번이 v1.4에서 추가됐다. 이유는 3.6절에 있다.

### 3.5 출력 데이터 구조

Gemini의 구조화된 출력(`response_mime_type: application/json` + 스키마 지정)을 사용한다.

```json
{
  "관련없음": false,
  "상황요약": "마지막 커밋에 포함되어야 할 파일이 빠진 상태로 보입니다.",
  "근거구분": {
    "확인됨": ["사용자가 커밋을 실행했다", "파일 하나가 누락됐다고 인지하고 있다"],
    "추정": ["아직 push하지 않았을 것으로 보인다"],
    "추가확인": ["git status 결과", "이미 push했는지 여부"]
  },
  "위험도": "주의",
  "오류위치": "local",
  "명령어": [
    {
      "cmd": "git status",
      "설명": "지금 어떤 파일이 어느 영역에 있는지 먼저 확인합니다.",
      "변경영역": [],
      "유지영역": ["work", "staging", "local", "remote"]
    },
    {
      "cmd": "git add 빠뜨린파일.txt",
      "설명": "빠뜨린 파일을 스테이징에 올립니다.",
      "변경영역": ["staging"],
      "유지영역": ["work", "local", "remote"]
    },
    {
      "cmd": "git commit --amend --no-edit",
      "설명": "새 커밋을 만들지 않고 직전 커밋에 합칩니다.",
      "변경영역": ["local"],
      "유지영역": ["work", "staging", "remote"]
    }
  ],
  "주의사항": [
    "이미 push한 커밋이라면 amend 후 강제 푸시가 필요합니다. 협업 중이라면 revert를 쓰세요."
  ],
  "그래프템플릿": "amend-add-file"
}
```

**필드 설명**

| 필드 | 타입 | 설명 |
|---|---|---|
| `관련없음` | boolean | Git과 무관한 질문이면 true |
| `상황요약` | string | 한 문장. 단정하지 말고 "~로 보입니다" 어투 |
| `근거구분` | object | `확인됨` / `추정` / `추가확인` 3개 배열 |
| `위험도` | enum | `안전` / `주의` / `위험` |
| `오류위치` | enum | `local` / `저장소관계` / `네트워크인증` / `github정책` / `판단불가` |
| `명령어[].변경영역` | array | `work` / `staging` / `local` / `origin-tracking` / `remote` |
| `명령어[].유지영역` | array | 위와 동일. **바뀌지 않는 영역도 명시** |
| `그래프템플릿` | enum | 3.7절의 템플릿 ID 또는 `none` |

**`근거구분`이 v1.4의 중요한 추가다.** AI는 사용자의 실제 저장소를 볼 수 없다. 그런데 v1.3까지의 스키마에는 그 불확실성을 표시할 자리가 없어서, 추측한 내용도 확정처럼 보였다. 초보자 대상 서비스에서 이는 위험하다. 결과 화면에서 세 항목을 시각적으로 다르게 표시한다(확인됨: 실선 테두리 / 추정: 점선 + 물음표 아이콘 / 추가확인: 회색 배경 + 입력 유도).

### 3.6 AI가 그래프를 직접 만들지 않는 이유

v1.3까지는 AI가 `before` / `after` 커밋 노드 배열을 생성했다. **이 설계를 폐지한다.**

문제는 세 가지다.

1. **AI는 사용자의 저장소를 볼 수 없다.** 생성된 커밋 ID와 그래프는 실제 상태가 아니라 창작이다.
2. **사용자가 자기 저장소로 오해한다.** "내 저장소가 이렇게 생겼구나"라고 믿고 명령을 실행한다.
3. **AI가 상황을 잘못 짚으면, 틀린 현실을 확신에 차서 그려 보여준다.** 텍스트 오류보다 그림 오류가 더 강하게 각인된다.

### 3.7 그래프 템플릿 방식

AI는 노드를 만들지 않고, **미리 검증한 템플릿 목록에서 하나를 고른다.** 렌더링은 프론트엔드가 검수된 데이터로 수행한다.

| 템플릿 ID | 설명 |
|---|---|
| `amend-add-file` | 직전 커밋에 파일을 합침 |
| `amend-message` | 직전 커밋 메시지 수정 |
| `restore-staged` | 스테이징만 되돌림 |
| `restore-worktree` | 작업 파일만 되돌림 |
| `revert-pushed` | 되돌리는 새 커밋을 추가 |
| `reset-soft` | 커밋 취소, 변경은 유지 |
| `non-fast-forward` | 원격이 앞서 push가 거절됨 |
| `fetch-updates-origin` | `origin/main`만 이동, 로컬 `main`은 유지 |
| `wrong-branch` | 다른 브랜치에서 작업한 커밋 이동 |
| `none` | 해당 없음 |

**`none`인 경우 그래프를 그리지 않고 영향 영역 표시만 한다.** 억지로 그리지 않는다.

그래프를 표시할 때는 상단에 항상 다음을 표기한다.

> 이 그림은 개념 예시입니다. 현재 저장소의 실제 그래프가 아닙니다.

이 방식의 이점은 세 가지다. AI가 시각화를 주도하되 창작은 못 한다. 그려지는 모든 그래프가 사전 검증을 거친다. 그리고 **동적 노드 렌더링 디버깅이 사라져 개발 시간이 줄어든다.**

### 3.8 실패 처리 기준

| 상황 | 판정 조건 | 메시지 | 처리 |
|---|---|---|---|
| 빈 입력 | 공백 제거 후 5자 미만 | "어떤 상황인지 조금만 더 자세히 적어주세요." | 전송하지 않음 |
| 입력 초과 | 1,000자 초과 | "1,000자 이내로 줄여주세요. (현재 N자)" | 전송하지 않음 |
| 민감정보 의심 | 토큰 형태 패턴 감지 | "API 키로 보이는 값이 있습니다. 지우고 보내주세요." | 전송하지 않음 |
| Git 무관 | `관련없음`이 true | "Git 관련 상황만 도와드릴 수 있어요." | 안내만 표시 |
| 응답 지연 | 5초 경과 | "명령어를 정리하고 있어요. 잠시만요." | 로딩 문구 교체 |
| 타임아웃 | 20초 경과 | "응답이 너무 오래 걸립니다. 다시 시도해주세요." | 요청 중단, 재시도 버튼 |
| 한도 초과 | 429 반환 | "지금 이용자가 많습니다. 30초 후 다시 시도해주세요." | 재시도 버튼 |
| 서버 오류 | 5xx 반환 | "일시적인 문제가 발생했습니다." | 재시도 버튼 |
| 형식 오류 | JSON 파싱 실패 | "결과를 불러오지 못했습니다." | 1회 자동 재시도 후 안내 |
| 템플릿 불일치 | `그래프템플릿`이 목록에 없음 | (사용자에게 노출 없음) | `none`으로 처리, 그래프 생략 |

과제 요구사항은 최소 1개를 요구하지만, 빈 입력 / API 오류 / 지연을 모두 구현한다.

| V4 | 가상 동료 fetch 시간차 데모 | 섹션 2 | 고정 3단계 애니메이션 | 보너스 |

### 4.1 V1 — 5영역 다이어그램

**세로 배치**를 채택한다. 모바일에서 좌우 스크롤 없이 읽힌다.

**구성 요소**

- 박스 3개: 작업 폴더 / 스테이징 영역 / 로컬 저장소
- **로컬 저장소 박스 안에 포인터 2개**: `main`(실선 라벨), `origin/main`(점선 라벨 + "마지막 fetch 기록" 배지)
- 박스 1개: GitHub `main` (서버 프레임)
- 점선 컨테이너: "내 컴퓨터 (로컬)" — 앞의 세 박스를 감쌈
- 화살표: `git add`, `git commit`, `git push`, `git fetch`, `git merge`, `git restore`, `git restore --staged`

**v1.3 대비 변경점 — `origin/main`을 별도 포인터로 그린다.** 이것이 없으면 `fetch`가 무엇을 바꾸는지 그릴 수 없다. `origin/main`이 점선인 이유는 "실제 원격이 아니라 기록"임을 색 외의 수단으로도 구분하기 위해서다(8.3절).

**화살표 정의 (v1.4 정정 반영)**

| 명령 | 출발 | 도착 |
|---|---|---|
| `git add` | 작업 폴더 | 스테이징 |
| `git commit` | 스테이징 | 로컬 `main` |
| `git restore <파일>` | **스테이징** | 작업 폴더 |
| `git restore --staged <파일>` | 로컬 `main`(HEAD) | 스테이징 |
| `git push` | 로컬 `main` | GitHub `main` (+ `origin/main` 갱신) |
| `git fetch` | GitHub `main` | 로컬 저장소 + `origin/main` |
| `git merge origin/main` | `origin/main` | 로컬 `main` + 작업 폴더 |

`git pull`은 별도 화살표를 그리지 않고, `fetch`와 `merge` 두 화살표를 연달아 강조하는 방식으로 표현한다. **`pull`이 두 동작의 합이라는 것을 그림으로 보여주기 위해서다.**

### 4.2 V2 — 커밋 그래프 (템플릿 기반)

`js/graph-templates.js`에 검증된 노드 배열을 둔다. AI나 정적 카드가 반환한 템플릿 ID로 조회해 렌더링한다.

**그리는 요소는 네 가지로 제한한다.** 커밋 원 / 부모 연결선 / 브랜치·HEAD 라벨 / 강조 색상.

```
반지름  r  = 13
원 간격 gap = 110
시작 x  x0 = 40
중심 y   y = 60
i번째 원의 x = x0 + i * gap
연결선  (x0 + i*gap + r, y) → (x0 + (i+1)*gap - r, y)
라벨    원 중심 위 y - 34
SVG 폭  x0 * 2 + (n-1) * gap + r * 2
```

**제한** — 커밋 최대 7개, 브랜치 최대 2개, 애니메이션 없음. 템플릿 작성 시점에 이 제한을 지키므로 초과 처리 로직이 불필요하다(v1.3 대비 단순화).

**상단 고정 문구** — "이 그림은 개념 예시입니다. 현재 저장소의 실제 그래프가 아닙니다."

## 6. API 명세

### `POST /api/rescue`

**요청**

```json
{
  "situation": "커밋했는데 파일 하나를 빼먹었어요",
  "executedCommand": "git commit -m \"기능 추가\"",
  "errorMessage": "",
  "statusOutput": "",
  "alreadyPushed": "unknown",
  "level": "beginner"
}
```

| 필드 | 타입 | 필수 | 설명 |
|---|---|:---:|---|
| `situation` | string | O | 5~1,000자 |
| `executedCommand` | string | X | 300자 이내 |
| `errorMessage` | string | X | 1,000자 이내 |
| `statusOutput` | string | X | 1,000자 이내 |
| `alreadyPushed` | enum | X | `yes` / `no` / `unknown` (기본) |
| `level` | enum | O | `beginner` / `intermediate` |

**응답 (200)** — 3.5절 구조

**응답 (400)**

```json
{ "error": "INVALID_INPUT", "message": "상황 설명이 너무 짧습니다." }
```

**응답 (429)**

```json
{ "error": "RATE_LIMITED", "message": "지금 이용자가 많습니다.", "retryAfter": 30 }
```

**응답 (500 / 502)** — AI API 오류 또는 응답 형식 오류

서버는 Gemini의 오류 코드를 그대로 전달하지 않고 위 형태로 정규화한다. **내부 stack trace나 API 응답 원문을 노출하지 않는다.**

**서버 측 검증** — 입력 길이는 프론트와 백엔드에서 모두 확인한다. 응답의 `그래프템플릿` 값이 허용 목록에 없으면 서버가 `none`으로 치환한 뒤 전달한다.

## 7. 보안 및 안전 설계

### 7.1 API 키 관리

| 환경 | 방법 |
|---|---|
| 로컬 | `.env`에 `GEMINI_API_KEY=...` |
| 배포 | Vercel → Settings → Environment Variables |
| 저장소 | `.gitignore`에 `.env` 포함. `.env.example`에는 키 이름만 |

키는 서버리스 함수 안에서만 `os.environ`으로 읽는다. 프론트엔드 코드나 네트워크 응답에 포함하지 않는다.

키 유출이 의심되면 **먼저 AI Studio에서 폐기·재발급하고, 그다음 커밋 이력을 정리한다.** 순서를 바꾸면 정리하는 동안에도 키가 유효하다.

### 7.2 요청 한도 대응

- **정적 카드 우선 (효과 최대)** — 흔한 상황 8개는 AI를 호출하지 않는다
- 전송 버튼을 누른 뒤 10초간 비활성화
- 동일 입력은 `sessionStorage`에 캐시
- 입력 길이 제한으로 토큰 사용량 억제
- 구조화된 출력으로 파싱 실패 재호출 방지
- 실패 시 1초 → 2초 → 4초 간격 재시도 (최대 3회)

요청 한도는 프로젝트 단위로 적용되므로 키를 여러 개 만들어 우회하지 않는다.

### 7.3 데이터 취급

무료 등급에 보낸 입력과 출력은 모델 개선에 사용될 수 있다. 사용자가 git 로그를 붙여넣는 구조이므로 토큰이나 사내 경로가 섞일 위험이 있다.

- 입력창 하단 민감정보 안내 상시 노출
- **토큰 형태 패턴을 감지하면 전송 전 경고** (예: `gh[pousr]_`, `sk-`, 40자 이상 16진 문자열)
- 사용자 입력을 저장하지 않음 (서버 무상태)
- AI 응답은 텍스트로 렌더링하고 임의 HTML을 실행하지 않음
- 푸터에 무료 등급 사용 사실과 데이터 취급 방침 명시

### 7.4 위험 명령 게이트 (v1.4 전면 개정)

**v1.3의 설계는 위험했다.** 백업 브랜치를 만들면 안전하다는 인상을 주지만, `git branch backup-...`은 **이미 커밋된 기록만** 보호한다. 다음은 보호하지 못한다.

- 아직 커밋하지 않은 작업 폴더의 수정
- 스테이징에만 있는 내용

즉 `git reset --hard` 앞에 백업 브랜치를 놓는 것은 **거짓 안심**이다. 정작 가장 잃기 쉬운 것을 지키지 못한다.

**개정된 6단계 게이트**

`위험도`가 `위험`인 결과는 다음 순서를 밟아야 명령어 복사가 활성화된다.

| 단계 | 내용 | 명령 |
|---|---|---|
| 1 | 현재 상태 확인 | `git status` |
| 2 | 무엇을 잃게 되는지 확인 | `git diff` / `git diff --staged` |
| 3 | 미커밋 변경이 있다면 먼저 대피 | `git stash push -u -m "backup"` 또는 임시 커밋 |
| 4 | 커밋 기록 보호가 필요하면 백업 브랜치 | `git branch backup-$(date +%Y%m%d-%H%M%S)` |
| 5 | **예상 손실 목록 확인** | (화면에 표시) |
| 6 | 위험 명령 복사 | (여기서 활성화) |

**5단계의 손실 목록**을 명시적으로 보여준다.

> 이 명령을 실행하면 다음이 사라집니다.
> - 작업 폴더에서 수정했지만 커밋하지 않은 내용
> - 스테이징에만 올린 내용
>
> 다음은 남습니다.
> - 커밋된 기록 (reflog로 찾을 수 있음)
> - Git이 추적하지 않는(untracked) 파일

**단, 잠금을 우회할 수단은 남긴다.** 명령어 텍스트는 드래그로 선택 가능하게 두고, "확인했습니다, 그냥 진행" 링크를 작게 배치한다. 사용자의 판단을 완전히 막는 것이 목적은 아니다.

### 7.5 reflog 안내 범위 (v1.4 정정)

v1.3의 "사라진 작업은 `git reflog`로 복구할 수 있다"는 문구를 폐기한다. **가장 위험한 상황에서 정확히 틀리기 때문이다.**

서비스에서 사용할 정확한 문구는 다음과 같다.

> `git reflog`는 **이동하거나 삭제된 커밋**을 찾는 데 유용합니다.
> 다만 **한 번도 커밋하지 않은 파일 변경까지 복구해주지는 않습니다.**
> 그래서 위험한 명령 전에 먼저 커밋하거나 stash해두는 것이 중요합니다.

이 구분이 7.4절 게이트의 3단계가 존재하는 이유이며, 두 곳에서 같은 메시지를 반복해 강화한다.

### 7.6 참고 자료 라이선스

Pro Git 2판(CC BY-NC-SA 3.0)을 개념 참고에 사용했다. **문장과 그림은 전부 새로 만든다.** 서비스 푸터에 참고 문헌으로 표기한다. 라이선스 대응이면서 과제의 "템플릿 복제 금지" 조항에도 부합한다.

## 8. 반응형 · 접근성 · 테마

### 8.1 반응형

| 구간 | 폭 | 레이아웃 |
|---|---|---|
| 모바일 | ~767px | 1단. 햄버거 메뉴. V2 그래프는 가로 스크롤 |
| 태블릿 | 768~1023px | 2단. 가로 메뉴 |
| 데스크톱 | 1024px~ | 최대 폭 1,120px. 결과 영역 2단(명령어 / 그래프) |

V1은 세로 배치라 모든 구간에서 동작한다. 대응이 필요한 것은 V2뿐이며, `viewBox`로 그리되 모바일에서는 `overflow-x: auto`와 최소 폭을 지정한다. 억지로 축소하면 라벨이 읽히지 않는다.

**모바일에서도 "내 컴퓨터"와 "GitHub" 제목이 항상 보이게 한다.** 이 경계가 서비스의 핵심 메시지이므로 스크롤 중에도 잃어버리면 안 된다.

검증은 375px / 768px / 1280px 및 실제 스마트폰 1대에서 수행한다.

### 8.2 접근성 (v1.4 신설)

- 모든 폼 요소에 `label` 연결
- **키보드만으로 네비게이션, 입력, 실행, 결과 확인 가능**
- 초점 표시(`:focus-visible`)를 제거하지 않음
- **색 외에 선 종류·아이콘·텍스트로도 상태를 구분한다.** V1의 `origin/main` 점선 라벨, 위험도 배지의 아이콘+텍스트 병기가 이에 해당
- 결과 표시 영역에 `aria-live="polite"`
- SVG에 `role="img"`과 `<title>` / `<desc>` 제공
- `prefers-reduced-motion` 존중
- 색 대비 WCAG AA 목표

**색만으로 위험도를 구분하지 않는 것**이 특히 중요하다. 이 서비스에서 위험도를 놓치면 데이터를 잃는다.

### 8.3 다크 모드 (보너스, 40시간 밖)

핵심 기능과 안전 검증이 끝난 뒤에만 착수한다. **다만 색상을 CSS 변수로 정의하는 작업은 처음부터 한다.** 나중에 하드코딩을 찾아 바꾸는 것은 몇 배로 오래 걸린다.

우선순위는 `localStorage` 저장값 → `prefers-color-scheme` → 라이트 모드 순이다. 토글 버튼은 상단 네비게이션 우측에 두고, 첫 페인트 전 적용을 위해 테마 결정 스크립트를 `<head>`에 인라인으로 넣는다.

**SVG 색상도 반드시 변수로 지정한다.** 하드코딩하면 다크 모드에서 검은 배경에 검은 선이 되어 시각화가 무의미해진다.

## 9. 테스트 케이스

### 9.1 정확성 (v1.4 최우선)

| # | 확인 항목 | 기대 결과 |
|---|---|---|
| 1 | `git add` 후 `git restore <파일>` | 작업 폴더가 **바뀌지 않음**을 설명에 명시 |
| 2 | `git restore --source=HEAD` 안내 | 마지막 커밋 상태로 되돌리는 방법으로 제시 |
| 3 | `git fetch` 설명 | "확인만"이 아니라 "객체를 받아 `origin/main` 갱신"으로 서술 |
| 4 | `git log origin/main..main` 카드 | 마지막 fetch 결과와 비교한다는 주의 문구 포함 |
| 5 | V1 다이어그램 | `main`과 `origin/main`이 서로 다른 포인터로 표시 |
| 6 | reflog 안내 | 커밋되지 않은 변경은 복구되지 않음을 명시 |

**이 6개는 배포 전 반드시 통과해야 한다.** 실제 저장소에서 명령을 직접 실행해 확인한다.

### 9.2 AI 기능

| # | 입력 | 기대 결과 |
|---|---|---|
| 7 | "방금 커밋했는데 오타를 발견했어요" | `git status` 우선, 변경/유지 영역 표시 |

## 10. 개발 일정

### 10.1 v1.4에서 일정을 다시 짠 이유

v1.1부터 v1.3까지 세 번의 개정에서, 매번 **기존 항목의 시간을 깎아 신규 기능을 끼워 넣었다.** 총합은 계속 40시간이었지만 실제로 줄어든 것은 검수와 튜닝 시간이었다. Git 답변은 틀리면 사용자가 데이터를 잃으므로, 이 방식은 위험하다.

이번에는 **핵심만으로 40시간이 찬다는 사실을 인정하고, 보너스를 전부 40시간 밖으로 분리한다.**

### 10.2 핵심 (40시간)

| 단계 | 작업 | 시간 |
|---|---|---:|
| 1 | 저장소 생성, 폴더 구조 구성 | 1h |
| 2 | **빈 페이지로 Vercel 배포 먼저 성공시키기** | 1h |
| 3 | HTML 마크업 및 5개 섹션 골격 | 2h |
| 4 | **CSS 변수 체계 설계** 및 레이아웃 | 4h |
| 5 | 네비게이션 / 햄버거 / 키보드 이동 | 2h |
| 6 | **V1 5영역 다이어그램 SVG** | 3h |
| 7 | `api/rescue.py` 구현, 로컬에서 Gemini 호출 성공 | 4h |
| 8 | 프롬프트 설계 및 출력 스키마 튜닝 | 4h |
| 9 | 프론트 연동 및 결과 렌더링 (근거구분 포함) | 3h |
| 10 | **그래프 템플릿 9종 작성 + V2 렌더러** | 3h |
| 11 | **정적 카드 8종 작성 및 실제 저장소 검수** | 3h |
| 12 | 위험 명령 6단계 게이트 | 1h |
| 13 | 실패 처리 10종 구현 | 3h |
| 14 | 명령어 사전 13개 콘텐츠 작성 | 2h |
| 15 | 반응형 + 접근성 검증 | 2h |
| 16 | 최종 배포, 수정, README·증빙 | 2h |
| | **합계** | **40h** |

### 10.3 보너스 (40시간 밖 — 실제로 시간이 남을 때만)

| 순위 | 작업 | 시간 | 비고 |
|---|---|---:|---|
| 1 | 다크 모드 + 토글 | 2h | 4번에서 변수 체계를 잡아두면 가능 |
| 2 | V4 가상 동료 fetch 데모 | 2h | 고정 3단계 애니메이션. 교육 효과 큼 |
| 3 | V3 영향 영역 하이라이트 | 1h | 마이크로 인터랙션 |
| 4 | V1 hover 인터랙션 | 1h | 모바일은 탭 대응 필요 |

**보너스 4개 중 하나만 완성해도 과제의 보너스 항목은 충족된다.** 1번이 비용 대비 효과가 가장 높다.

### 10.4 위험 구간과 중단 기준

| 단계 | 위험 | 중단 기준 |
|---|---|---|
| 8 (프롬프트 튜닝) | 끝이 없음 | 테스트 7~11번 통과 시 종료 |
| 11 (정적 카드 검수) | 시간 초과 | 8개를 못 채우면 **개수를 줄이되 검수는 생략하지 않는다** |
| 10 (그래프 템플릿) | 좌표 조정 반복 | 커밋 7개 / 브랜치 2개 제한 준수 |

**시간이 부족할 때 잘라낼 순서** — 보너스 4개 → 명령어 사전 13개를 8개로 → 정적 카드 8개를 5개로 → V2 그래프 전체(영역 표시만 유지).

**절대 자르지 않는 것** — 9.1절 정확성 테스트 6개, 7.4절 위험 게이트, 13번 실패 처리. 이 셋은 서비스가 사용자에게 해를 끼치지 않기 위한 최소선이다.

## 부록 A. 학습 목표 대응표

| 학습 목표 | 대응 근거 |
|---|---|
| HTML/CSS/JS의 역할 | `index.html`(구조) / `style.css`(표현) / `rescue.js`(동작) 분리 |
| 입력 → fetch → 화면 반영 | 폼 입력 → `fetch('/api/rescue')` → JSON 파싱 → SVG 렌더링 |
| Serverless Functions 구조 | `api/rescue.py`가 요청마다 실행되고 응답 후 종료되는 무상태 구조 |
| 환경 변수로 키를 관리하는 이유 | 프론트에 키를 두면 브라우저 개발자 도구에서 그대로 노출됨 |
| 로컬과 배포 환경의 차이 | 로컬 `.env` vs Vercel 환경 변수 |
| 오류 원인 파악과 수정 | 실패 처리 10종을 직접 설계하며 각 오류의 발생 지점을 구분 |

**주목할 점** — 이 서비스가 설명하는 "내 컴퓨터와 GitHub의 분리"는, 개발자 본인이 겪는 "로컬 환경과 Vercel 배포 환경의 분리"와 같은 구조다. 로컬에서는 되는데 배포하면 안 되는 이유를 이해하는 과정이 곧 서비스의 콘텐츠가 된다. 2.6절에 기록한다.
